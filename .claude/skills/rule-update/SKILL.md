# 규칙 갱신 절차

정책 수치는 `docs/sources/` → 규칙 JSON → 골든 케이스 순서로만 흐릅니다. 이 순서를 건너뛰지 않습니다.

## 1. 범위 정하기
- 어떤 상품인지, 재검증인지 수치 변경인지, 새 상품 추가인지 확인합니다.
- 해당 `docs/sources/<상품>.md` 맨 위의 원문 URL과 확인일을 봅니다.

## 2. 원문 대조 (이때만 원문을 읽음, D-17)
- 원문 페이지를 열어 **판정에 쓰는 값만** 대조합니다: 소득·순자산 상한, 혼인 요건, 대상 주택, 한도, 금리표, 가감·우대, 하한.
- 페이지 전체를 요약하거나 복사하지 않습니다.
- 달라진 값은 "이전 → 이후"로 목록을 만듭니다. 바뀐 게 없으면 4번으로 바로 갑니다.

## 3. 반영 (한 커밋으로 묶음)
1. `docs/sources/<상품>.md`: 값, 확인일, "재검증" 메모 갱신
2. `packages/rules-data/products/<id>.json`: 같은 값과 `effectiveFrom`, `source.checkedAt` 갱신
3. `docs/golden-cases.md`: 영향받는 케이스의 기대값과 "원문 근거" 표 갱신. 경계값 케이스가 없으면 추가
4. 새 용어가 생기면 `docs/GLOSSARY.md`에 추가
5. 새 상품이면 `docs/sources/README.md` 표에도 추가

## 4. 검증
```bash
pnpm --filter @jipgak/rules-data validate
pnpm test
```
- 실패하면 골든 기대값부터 원문과 다시 대조합니다. 테스트에 맞추려고 규칙을 바꾸지 않습니다.

## 5. 기록
- `docs/sources/README.md`의 확인일을 갱신합니다.
- `docs/STATUS.md`에 "출처 재검증 완료(날짜, 변경 요약)"를 남기고, 다음 재검증 예정월(3개월 뒤)을 적습니다.
- 커밋 메시지: `rules: <상품> <변경 요약> (YYYY-MM-DD 원문 기준)`

## 하지 말 것
- `docs/sources/`에 없는 수치를 규칙에 넣기
- 블로그·비교 사이트 수치 사용 (공식 원문만)
- sources, 규칙, 골든을 나눠서 커밋하기
